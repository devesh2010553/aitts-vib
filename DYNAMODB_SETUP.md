# DynamoDB Setup — AITTS

Three tables replace `Test`, `UserProfile`, and `Result` from MongoDB. Everything else
(chat, ad images, PDF imports, the leaderboard cache, forgot-password attempts) stays
on MongoDB, untouched.

Create these **exactly as specified** — the code in `backend/dynamo/*.js` references
these table/index names and key structures directly. Region: use `ap-south-1` (Mumbai)
unless you have a specific reason not to — it's closest to India, where your students are.

Billing mode: **On-Demand** for all three tables. This is the one that matters most —
On-Demand auto-scales without you pre-guessing a read/write capacity number, and (per
the earlier discussion in this conversation about AWS billing surprises) you can set a
**maximum** on-demand throughput per table as a safety ceiling against a runaway bug,
which Provisioned mode can't give you as cleanly. Do this for all three tables once
created: **Table → Additional settings → Read/write capacity → Maximum throughput →
set a number** (e.g., 1000 — comfortably above your real traffic, nowhere near what
an accidental infinite-loop bug could rack up).

---

## 1. AIITS_Users

**Table name:** `AIITS_Users`
**Partition key:** `uid` (String) — this is the Firebase uid directly, not a separate
generated id.

### Indexes (create both, under "Indexes" tab → Create index)

**GSI: `PhoneIndex`**
- Partition key: `phone` (String)
- Projection: All attributes
- Used for: best-effort duplicate-phone check on registration (see the caveat
  in `backend/dynamo/userModel.js` — this is NOT a hard uniqueness guarantee
  the way Mongo's unique index was)

**GSI: `RankIndex`**
- Partition key: `gsiType` (String)
- Sort key: `totalMarks` (Number)
- Projection: All attributes
- Used for: the public top-performers query and the (mostly legacy) `/rankings/leaderboard`
  route — "every student, sorted by totalMarks," without a full table scan. Every user item
  the app writes sets `gsiType: 'USER'` (a constant) specifically so this GSI has one
  partition to query across the whole table.

---

## 2. AIITS_Tests

**Table name:** `AIITS_Tests`
**Partition key:** `testId` (String) — generated by the app (`test_<uuid>`), not
auto-assigned by DynamoDB.

### Index

**GSI: `PublishedIndex`**
- Partition key: `isPublished` (String — the literal strings `"true"`/`"false"`, not a
  DynamoDB boolean; DynamoDB key attributes can't be boolean type)
- Sort key: `createdAt` (String — ISO timestamp)
- Projection: All attributes
- Used for: the student dashboard's "list published tests, newest first" query.

---

## 3. AIITS_Results

**Table name:** `AIITS_Results`
**Partition key:** `userId` (String) — same uid as `AIITS_Users`.
**Sort key:** `testId` (String) — same id as `AIITS_Tests`.

This composite key is what replaces Mongo's unique `{userId, testId}` index — a
`GetItem` on this exact pair *is* that lookup now, not a secondary index.

### Indexes (create both)

**GSI: `TestIndex`**
- Partition key: `testId` (String)
- Sort key: `obtainedMarks` (Number)
- Projection: All attributes
- Used for: per-test rankings/leaderboard — "everyone who took this test, by score."
  Tie-breaking by time is done in application code after this query returns (DynamoDB
  sort keys are a single attribute, can't encode a two-part sort).

**GSI: `BatchIndex`**
- Partition key: `batch` (String)
- Sort key: `testId` (String)
- Projection: All attributes
- Used for: the cumulative class leaderboard — "every result for this class," queried
  once per batch (up to 3 times for the "All" filter, once for a specific class).

## 4. IAM user for your Render backend

Don't use root AWS credentials. Create a dedicated IAM user scoped to only what this
app needs:

1. AWS Console → **IAM** → **Users** → **Create user**
2. Name it something identifiable, e.g. `aitts-render-backend`
3. **Attach policies directly** → search for `AmazonDynamoDBFullAccess` and attach it.
   (Full access to DynamoDB specifically is fine here since this IAM user has no
   access to anything else — S3, EC2, etc. — by default; you're not granting broad
   AWS access, just broad *DynamoDB* access to a user that can't touch anything else.)
4. Click into the new user → **Security credentials** tab → **Access keys** →
   **Create access key** → choose **Application running outside AWS** → create.
5. Copy both the **Access key ID** and **Secret access key** immediately — the secret
   is shown once.

## 5. Set the environment variables

On Render (and locally in `.env` for testing), set:

```
AWS_REGION=ap-south-1
AWS_ACCESS_KEY_ID=<the access key from step 4>
AWS_SECRET_ACCESS_KEY=<the secret key from step 4>
```

The table names default to `AIITS_Users`/`AIITS_Tests`/`AIITS_Results` — only set
`DYNAMODB_TABLE_USERS`/`DYNAMODB_TABLE_TESTS`/`DYNAMODB_TABLE_RESULTS` if you named
your tables differently from the spec above.

**Never** put these in the frontend or commit them to GitHub — same rule as
`MONGODB_URI`, they belong only in Render's environment variable settings.

## 6. What changed for existing MongoDB data

This is a fresh start on DynamoDB — there is no automatic migration of your existing
Mongo `Test`/`UserProfile`/`Result` documents into these new tables. Your old MongoDB
data is untouched and still sitting in your MongoDB cluster (nothing was deleted), but
the app will not read from it anymore once these three tables are configured — it's a
clean cutover, not a gradual one.

If you need your existing students/tests/results to carry over rather than starting
fresh, that's a one-time data-migration script (read from Mongo, write into these three
DynamoDB tables via the `create()`/`submit()` functions in `backend/dynamo/*.js` so the
data goes through the same normalization those functions already do) — not included
here since you hadn't asked for that yet; say the word if you want it before going live.

## 7. Verify before deploying

Once the tables exist and env vars are set, start the app locally (`npm install && npm start`)
and check the startup log for `[DYNAMO] Missing env vars` — if that doesn't print, the
client initialized. Then:
- Register a test student account → confirms `AIITS_Users` writes work.
- Log in as admin, create a test, publish it → confirms `AIITS_Tests` + `PublishedIndex`.
- Take that test as the student, submit → confirms `AIITS_Results`, `TestIndex`, rank
  calculation, and the `AIITS_Users` stat update all work together.
- Open the Leaderboard tab, both "All" and a specific class → confirms `BatchIndex`
  and the per-batch cumulative math.

If any step 500s, the error message will name the missing table/index — the four
names above (`PhoneIndex`, `RankIndex`, `PublishedIndex`, `TestIndex`, `BatchIndex`)
are the only ones that matter; a typo in any of them is the most likely first issue.
